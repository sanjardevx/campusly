# Campusly — Architecture Decisions

Source of truth for decisions agreed in the architecture chat ("eCampus architecture va stack maslahat") and the design chat ("eCampus 2").
When a decision changes, update it here **and** add a line to the [Decision log](#decision-log) at the bottom.

---

## 1. Product

- **Campusly** is a K-12 **learning platform (LMS)** for one private school in Tashkent. It is **not** a school-management system.
- Roles: `ADMIN`, `TEACHER`, `STUDENT`, `PARENT`.
- One deployment per school (no multi-tenancy, no `schoolId` columns). School name, logo and colors come from env / admin settings.
- Branding: portal = "Campusly"; public site = "Campusly School". ("Campusly Academy" was rejected.)
- **Out of scope:** timetable, rooms, homeroom teacher, lessons-per-week, SMS.

## 2. Repository layout

- One GitHub repo `campusly`, **no Turborepo**. Branches: `develop` (default, daily work) and `master` (releases).
- `backend/` — NestJS in **monorepo mode**, same idea as Nestar's `nestar-api` + `nestar-batch`:
  - `apps/campusly-api` — GraphQL API + REST `/auth/*`
  - `apps/campusly-batch` — worker (BullMQ jobs, cron)
  - `prisma/` at backend root (shared by api and batch)
- `frontend/` — Next.js **Pages Router**, same structure as `nestar-next`.
- Root: `docker-compose.yml` (dev Postgres + Redis), `.github/workflows/ci.yml`, `docs/`, `CLAUDE.md`.

## 4. Code style (Nestar / Burak)

- Backend module = `components/<module>/{<module>.module.ts, <module>.resolver.ts, <module>.service.ts}`.
- Shared code in `libs/`: `libs/dto/<module>/`, `libs/enums/`, `libs/types/`, `libs/config.ts`, `libs/interceptor/`, `libs/utils/`.
- Guards/decorators keep Nestar names and spirit: `@Roles(...)`, `@CurrentUser()` (was `@AuthMember`), `@Public()` (replaces `WithoutGuard`).
- Data access: `this.prismaService.user.findMany(...)` instead of `this.memberModel.find(...)`. No extra repository layer.
- Resolver = thin (guards, args, call service). Service = business logic + ownership checks.
- Simple, readable code over abstractions. The author must be able to explain every line in an interview.
- Reference code: `~/DEVELOPMENT/DEVEX/nestar/nestar` (backend), `~/DEVELOPMENT/DEVEX/nestar/nestar-next` (frontend).

## 5. Database rules

- PK: **UUID v7** (`@default(uuid(7))`). `loginId` is a separate unique column, never a PK/FK.
- Raw-SQL inserts (e.g. `document_chunks`) must generate UUID v7 in app code (`uuid` package `v7()`), because `@default(uuid(7))` is generated by Prisma Client, not by Postgres.
- All instants: `@db.Timestamptz(3)` (UTC). Calendar dates (birth date, attendance date, period start/end): `@db.Date`.
- Scores: `Decimal(6,2)`. Store raw points (`18 / 20`); 5-point marks are presentation only.
- Enums stored as codes (`SUBMITTED`, not "Topshirildi"); the UI translates them.
- **No hard deletes.** Use `status` (`ACTIVE | BLOCKED | ARCHIVED`) and write `AuditLog` for important changes.
- Uniqueness is enforced in the DB with `@@unique`, e.g. `Enrollment[courseId, studentId]`, `Submission[assignmentId, studentId]`, `AttendanceRecord[sessionId, studentId]`, `ParentStudent[parentId, studentId]`, `LessonProgress[studentId, lessonId]`.
- Migrations: `prisma migrate dev` locally, `prisma migrate deploy` in production. Never `db push` against production. Dropping a column is a two-release change.

## 6. Login IDs and passwords

- **Login ID** (students/teachers): `YY` + role digit + 5-digit sequence. `1` = student, `2` = teacher. Example: `26100042`.
  - Generated atomically: `INSERT ... ON CONFLICT (year, roleCode) DO UPDATE SET lastValue = lastValue + 1 RETURNING lastValue`, inside the same transaction that creates the user. Never `MAX() + 1`.
- **Parent login ID:** last 9 digits of the phone number (e.g. `901234567`). One parent account can have many children; one child can have two parents.
- **No public signup.** Admin creates every account (single form or CSV import) and prints login slips.
- **Temporary passwords (final rule, same for parents and students):**
  - Valid for **N sign-ins or D days**, whichever comes first. N and D are a school setting (Settings → Accounts): default **3 / 14**, allowed 1–10 / 1–60. A change applies to passwords made from then on; passwords already handed out keep their rule.
  - Every sign-in with a temporary password shows a warning banner. **No forced change on first sign-in.**
  - When the limit is reached, only the "Set a new password" screen is available (`mustChangePassword = true`).
  - Fields: `tempPasswordUsesLeft` (starts at N), `tempPasswordExpiresAt` (+D days), `mustChangePassword`.
  - Student temp password: 8 chars (upper + digit + symbol). Parent temp password: readable format like `Rus6738#`.
- New password rules: 8–128 chars. Hash with `bcryptjs`.
- Login rate limit in Redis: 5 attempts per loginId per 15 min, 30 per IP per 15 min.
- Wrong credentials always return the same `INVALID_CREDENTIALS` (401) — never reveal whether the ID exists.
- A blocked (or archived) account gets `ACCOUNT_BLOCKED` (403) only after the correct password, so the code still does not reveal which IDs exist. An unknown ID is compared against a dummy bcrypt hash, so the response time does not reveal it either.

## 7. Authentication

- **Access token:** JWT, 15 min, payload only `{ sub, role, sid }` (+ `pwc` flag when a password change is required). `sid` = the refresh-token family of this sign-in, so `changePassword` can revoke the *other* sessions (the refresh cookie is not sent to `/graphql`). The frontend keeps it **in memory**, never in localStorage.
- **Refresh token:** random 32-byte string (not a JWT), stored in the DB as a sha256 hash.
  - Cookie: `httpOnly; Secure; SameSite=Lax; Path=/auth`, **no `Domain` attribute** (sent only to the API host).
  - Lifetime by role: parent 30 days, student/teacher 14 days, admin 1 day.
  - **Rotation + reuse detection:** each refresh revokes the old token and issues a new one in the same `familyId`. If a revoked token is used again, the whole family is revoked. A 10 s grace window covers parallel tabs.
  - Refresh also checks `user.status === ACTIVE`.
- REST endpoints: `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`. Everything else is GraphQL with `Authorization: Bearer <access>`.
- On page load the frontend calls `/auth/refresh` (silent refresh). Refresh calls are single-flight on the client.
- CSRF: GraphQL uses the Bearer header (not cookies). Cookie endpoints are POST-only, `SameSite=Lax`, and check `Origin` against the whitelist.
- Logout, password change and admin block revoke refresh tokens.

## 8. Authorization

- **Secure by default:** `JwtAuthGuard` and `RolesGuard` are global (`APP_GUARD`). Open endpoints are marked `@Public()`.
- Two layers:
  1. **Role** (`@Roles(...)` + `RolesGuard`): may this role call this operation?
  2. **Ownership** (`AccessPolicy` in services): may *this* user touch *this* record?
- `AccessPolicy` (one file, `components/auth/policies/access.policy.ts`):
  - `courseScope(user)` → Prisma `where` for lists (ADMIN `{}`, TEACHER via `CourseTeacher`, STUDENT via active `Enrollment`).
  - `assertCanViewCourse`, `assertTeacherOf`, `assertCanViewStudentInCourse`.
  - `resolveStudentScope(user, studentId?)`: STUDENT → always self (the param is ignored), PARENT → must have an active `ParentStudent` link, ADMIN → any.
- Rules:
  - The client sends only IDs. Ownership is always loaded from the DB.
  - Lists combine scope and user filters with `AND`, never by spreading objects.
  - No relation → `404 NOT_FOUND`. Related but forbidden action → `403 FORBIDDEN`.
  - Validate every ID inside input arrays (e.g. every `studentId` in `markAttendance` must be enrolled in that course; every `assetId` in `submitAssignment` must belong to the student).
  - GraphQL exposes purpose-built queries/DTOs (`myCourses`, `teachingCourses`, `courseRoster`, `studentOverview`), not generic relation fields like `Course.enrollments`.
  - Sensitive fields (`passwordHash`, temp-password data, `telegramChatId`) are omitted globally in Prisma.
  - Unpublished grades: score and feedback are hidden from students and parents by a single mapper.
- Parents never see AI tutor conversations. Teachers see only aggregated tutor topics (later phase).
- On logout the frontend clears the Apollo cache (`clearStore()`), because school computers are shared.
- Isolation tests (e2e, table-driven) must cover every new resolver with at least one "foreign user" case.

## 9. API conventions

- Errors return a **code**, not a sentence: `extensions.code` such as `INVALID_CREDENTIALS`, `PASSWORD_CHANGE_REQUIRED`, `NOT_FOUND`, `FORBIDDEN`, `RATE_LIMITED`. The frontend translates codes into 4 languages. (Nestar compared English message strings in the frontend.)
- Correct HTTP semantics: 400 / 401 / 403 / 404 / 429. Never 500 for user errors.
- Global `ValidationPipe({ whitelist: true })`; DTOs use `class-validator`.
- GraphQL: DataLoader for nested lists, depth/complexity limits, Playground and introspection off in production.
- Config is validated with `zod` at startup — a missing env var stops the app (fail fast).
- Logging: `LoggingInterceptor` redacts `password`, `token` and similar fields (Nestar logged raw `req.body`).
- CORS: only `FRONTEND_URL`, `credentials: true` (Nestar had `origin: true`).

- Validation the UI must explain gets its own error code (`IMPORT_*`, `WEIGHTS_SUM`, `PERIOD_OVERLAP` …; CSV rows: `ImportIssueCode` + the bad value). The client translates codes; messages are only for logs.
- **Records page (admin):** class lists, grades journal (course × quarter), attendance journal (course × date range), report card (one student, current quarter, published grades only). Files (CSV with a UTF-8 BOM, print view) are built in the browser from the normal policy-checked queries — nothing is stored on the server. Every download and print calls `logRecordExport` → `AuditLog` (`records.export`: who, which document, which class/course/student).
- **School settings hold only rules the system really uses:** name, default language, timezone, mark thresholds, default weights, office contact (phone and hours: sign-in page and login slips), two Telegram links — the school's **channel** (`https://t.me/…`, only on the public website footer) and the password-reset **bot** (`https://t.me/…bot`, the "Reset in Telegram" button under "Forgot password?", shown only when set) — and the temporary-password rule. Security limits (login rate limit, token lifetimes, upload sizes and types) stay in code / env: an admin must not be able to weaken them by accident.

## 10. Grading and attendance

- Course = subject × class (e.g. `Algebra · 9A`). Class students are enrolled automatically; split groups (e.g. Korean group 1/2) pick students manually.
- `GradeCategory` weights per course (school default Homework 30 / Quizzes 30 / Exams 40). Quarter % = weighted average of **published** grades; empty categories are skipped and the other weights rebalanced.
- 5-point mark thresholds come from school settings (default 5 ≥ 86%, 4 ≥ 71%, 3 ≥ 56%, else 2). The mark is shown next to the %.
- An assignment belongs to a period by its `dueAt`, with the period's days taken in the school timezone (a period ending on 31 Oct ends at 1 Nov 00:00 Tashkent). An assignment without `dueAt` is in no period.
- Inside a category, points are summed (`earned / possible`), not percents averaged: a 100-point exam weighs more than a 10-point quiz. A `MISSING` zero counts like any grade.
- Everyone (teachers too) sees the period % from **published** grades only, so all roles see the same number.
- `PeriodGrade`: computed live until the teacher publishes; publishing stores a snapshot (`computedScore`, optional manual `finalScore`). The annual grade is derived from period snapshots.
- Late submissions are allowed until grades are published (if `allowLate`). "Give 0 to not submitted" sets `MISSING`.
- Attendance is per **course session** (`ClassSession` by date), not per school day. Default status is `PRESENT`; teachers mark exceptions.
- **Admin dashboard "needs attention" is about attendance only** (current period, up to today): below 75 % → HIGH, 75–85 % → MEDIUM, 85–90 % → LOW. A rate needs at least 5 marks. Counted on the server (`groupBy`); the list shows the 5 lowest rates.
- **Teacher dashboard** (no timetable): "Attendance today" lists all of the teacher's active courses with today's state (taken / not taken; a HOLIDAY event today shows "no classes"), without periods, times or rooms. "Needs grading" = submitted / late work not graded yet (an exam past its date: students without a score), plus assignments fully graded but not published. Read receipts on the teacher's own announcements count the course's active students. The Stitch "Unanswered questions" card lists the newest questions of the teacher's courses that no teacher answered yet (day 21).
- **Course page (teacher, edit mode):** a week holds lessons (video, file, reading, link) and assignments (`Assignment.moduleId`); lessons first in their own order, then assignments by due date. A FILE lesson has one `LessonResource` (`setLessonFile`). Weeks and lessons are reordered by native drag and drop plus "Move up / Move down" in the ⋯ menu (keyboard, touch); no drag library. Course files (lesson files, assignment attachments) are opened through `courseFileUrl(assetId)`: a short-lived signed link, only for users who may see the lesson or assignment. Quiz stays "coming soon" in the Add menu until the quiz phase.
- **Grading page (teacher):** the table and the one-student view use `assignmentSubmissions` (active students in name order, signed file links). "Download all (ZIP)" is built in the browser (`fflate`) from those signed links, so files still never pass through the API. The weights modal (`setGradeCategories`) changes the course's own weights for all quarters: every existing category is sent back, names are unique (`CATEGORY_NAME_TAKEN`), the total is 100 (`WEIGHTS_SUM`), audited (`course.gradeCategories`). A category is never deleted (assignments point to it); weight 0 switches it off. The teacher's CSV export of their own gradebook is built in the browser and is not written to AuditLog (the audited exports are the admin Records page). The manual `finalScore` override has no UI yet.
- **Announcements (teacher):** the drawer sends one announcement to several of the teacher's courses with `createCourseAnnouncements` — one row per course (each with its own read count), all in one transaction. Attachments (`AnnouncementFile`) are the author's READY uploads for one of those courses, opened through `courseFileUrl`. ⋯ archives instead of deleting (`status = ARCHIVED`, audited `announcement.archive`); archived ones are hidden from everyone and cannot be edited. Staff see "studentReads / audience" (the course's active students; parents' reads are not counted). Notifications ("students are notified") wait for the Telegram / Socket.IO phases.

## 11. Media

- The browser uploads directly to S3 with a presigned URL; the API never streams files. Multipart upload (Uppy) comes later.
- `confirmUpload` verifies the object with `HeadObject` (size/type) before marking the asset `READY`.
- S3 keys are generated by the server (`raw/{courseId}/{assetId}.mp4`); original file names are stored only as metadata.
- Two buckets: `campusly-dev-media-*` (local development) and `campusly-prod-media` (the EC2 server, its own CloudFront → `media.campusly.uz`). The EC2 IAM role can reach only the prod bucket.
- The bucket is private (Block Public Access on) and served via CloudFront with OAC. CORS exposes `ETag`. A lifecycle rule aborts incomplete multipart uploads after 3 days.
- Playback: CloudFront signed URL (~3 h) for MP4; later HLS with signed cookies (`Domain=.campusly.uz`, path `/hls/{assetId}/`).
- Student ID watermark over the player; progress heartbeat every ~20 s; playback resumes from the last position.
- **Sequential watch rule** (until the lesson is completed): progress = how far the student got (`maxPositionSec`), and it grows only as fast as real time at 1× speed (+3 s tolerance per heartbeat). No speed-up above 1× and no seeking past the furthest point; seeking back is allowed. At 90% the lesson is `COMPLETED` and the player unlocks any speed and any position. The player enforces it for comfort (`lessonVideo.isLocked`, `maxSeekSec`); the server enforces it for real.

## 14. Phase 2 (days 15–21, minimal versions)

The project ends on **day 21**. Deploy comes first (days 14–15); after that each phase 2 feature is built in a minimal working version and deployed the same day (see PLAN.md):
Telegram bot (account linking, password reset link, BullMQ notifications) → quiz engine (MC / True-False / Number, timer, 1 attempt, auto-grade) → AI Study Tutor (PDF → pgvector, Bedrock Haiku 5.5, SSE, help levels 1–4, per-assignment `tutorMode`, daily limits + global budget) → public website + minimal CMS (News & Events, Programs, Our team, Enquiries) → the website's second part (Mock tests, Open Courses, Honor Students, motion, portal showcase) → Q&A and the calendar page for students / parents.

**AI Study Tutor (day 18).** RAG over the course's own material: the batch cuts published lessons (title + text), assignments (not quizzes, not tutor-OFF) and their PDFs into ~1 200-character pieces and embeds them (`DocumentChunk`, derived data rebuilt by hash — old pieces of a changed source are replaced). A question is embedded and the 5 closest pieces of THAT course are found with exact cosine search, filtered at question time to what the student may see (published, visible week). Help levels 1–4 (nudge → concept → step → similar example, never the final answer); "Show another hint" goes up one level, "I solved it" back to 1. The assignment's `tutorMode`: HINTS, CHECK_ONLY (only "right / not right" against the server-side `finalAnswer`), OFF (refused, like quizzes). While the student has a quiz attempt open the tutor refuses everything. Limits in Redis: `TUTOR_DAILY_LIMIT` requests per student per day (default 20; every model call counts; a failed call is given back) and $2 per day for the whole school (tokens × the provider's price, embeddings included); both reset at midnight Tashkent. Answers are short (max 1 024 tokens, effort low). The answer streams over SSE (`POST /tutor/chat`, fetch + reader because EventSource cannot send the Authorization header); lists, thread, status and "solved" are GraphQL, STUDENT only — parents and staff get FORBIDDEN, another student's conversation is NOT_FOUND. Production uses `TUTOR_PROVIDER=anthropic` (Anthropic API, prepaid credit with auto-reload off as the hard cap); only the question, the course material and the conversation are sent — no names or IDs.

**Public website + minimal CMS (day 19).** `/` is the school's website, built from the Stitch "Campusly Public" landing (Part A, B, C, desktop and mobile): hero slideshow (4 photos, dots, pause; no auto-play with reduced motion), live numbers (active students, teachers, programs on the site, founded year), News & Events slider (up to 5 posts in the admin's order; none chosen → the latest 3), Why choose, Programs & clubs (the first 6 on the site), Our team (director's card + the rest), School stages, Admission process, the enquiry form, FAQ and footer. The portal's front door moved to `/portal`. Static sections are translations (`site` namespace, 4 languages); CMS content is stored as `{ en, uz, ru, ko }` JSON — English required, a missing language falls back to English; drawers have EN / UZ / RU / KO tabs and "Translate from English" (the LLM fills only empty translations; the admin checks them; off until the model is connected). The page is static with ISR (rebuilt at most every 10 minutes, so a CMS change shows within that); uploaded pictures are private S3 objects shown through day-long signed CloudFront links; the seeded demo content uses the Stitch placeholder photos under `frontend/public/site` until the school uploads its own (an upload replaces the path). Admin CMS (Stitch "Campusly Admin — Website"): News & Events (publish now / schedule / draft, slider position), Programs (on-site switch, drag to reorder, photo or a YouTube link — MP4 upload is backlog, up to two teachers from "Our team"), Our team (one director, drag to reorder), Enquiries (Admissions; the Support tab waits for a portal help-request feature). Footer details (address, metro, email, Instagram, YouTube, founded) are a "Public website" card in Settings.

**Public website, part 2 (day 20).** Three more CMS sections, same rules as day 19 (4-language JSON with English fallback, archive instead of delete, audited, admin only):

**Course Q&A (day 21).** `CourseQuestion` + `CourseAnswer`.
